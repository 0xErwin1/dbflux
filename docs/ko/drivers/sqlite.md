# SQLite

파일 기반 내장 데이터베이스입니다.
## 한눈에 보기

- **분류** — 관계형
- **쿼리 언어** — SQL
- **URI 스킴** — `sqlite`

## 기능

- 파일 기반 데이터베이스 경로를 사용하는 내장 SQLite 관계형 드라이버입니다.
- SQL 실행, 스키마 검색, 뷰, 인덱스, 외래 키, CHECK 제약 조건, UNIQUE 제약 조건을 지원합니다.
- SQLite 인터럽트 핸들을 통한 쿼리 취소를 지원합니다.
- CRUD, 인덱스, reindex, 테이블 생성, 테이블 삭제를 위한 SQL/코드 생성을 포함합니다.
- 다중 문 스크립트(여러 개의 `;`로 구분된 문)는 문별로 분할되어 실행되며, 각 문은 타입이 지정된 prepared 경로를 거쳐 문마다 하나의 결과 집합을 반환합니다. (`rusqlite::prepare`는 문자열의 첫 번째 문만 파싱하므로 스크립트는 분할되어야 합니다.)
- 데이터 전송 엔진: 네이티브 다중 행 `INSERT` 대량 적재(`BULK_INSERT`), 원본 테이블의 열을 기반으로 한 드라이버 네이티브 `CREATE TABLE` DDL, FK 안전 마이그레이션을 위한 연결별 참조 무결성 토글(`PRAGMA foreign_keys`).

## 제한 사항

- 로컬 파일 드라이버 전용입니다. 네트워크 전송, SSH 터널링, TLS/SSL 모드가 없습니다.
- SQL 전용 드라이버입니다. 문서 또는 키-값 API를 노출하지 않습니다.
- SQLite 스키마 모델에는 서버 측 다중 스키마 네임스페이스에 해당하는 것이 없습니다.
- `TRUNCATE TABLE` 문이 없습니다. 데이터 전송 엔진의 Truncate 적재 옵션은 SQLite 대상에 대해 사용할 수 없습니다(`DriverCapabilities::TRUNCATE_TABLE`이 설정되지 않음).

## DDL 지원 범위

### 트랜잭션 DDL

SQLite는 **트랜잭션 DDL**을 지원합니다 — 수동 DDL 작업은 트랜잭션으로 감싸고 롤백할 수 있습니다:

```sql
BEGIN;
ALTER TABLE users ADD COLUMN phone TEXT NULL;
-- 변경을 테스트합니다
ROLLBACK;  -- 문제가 생기면 롤백해도 안전합니다
```

관리형 테이블 변경은 다릅니다: 드라이버가 테이블별 트랜잭션을 소유하기 때문에 그 플래너는 자동 커밋
연결을 필요로 합니다.

### 관리형 ALTER TABLE

순수한 `DROP COLUMN` 요청에 대해서는, 링크된 SQLite 버전이 이를 지원하는 경우 DBFlux가 SQLite의 네이티브 `DROP COLUMN`
경로를 먼저 사용합니다. 네이티브 삭제는 SQLite 자체의 수용 규칙을 따르며, 재구축 문법의 제한을 받지 않습니다. DBFlux는 여전히
알려진 의존성을 사전 점검하고 SQLite가 실행 시점에 요청을 다시 검증합니다.

선택된 타입, nullability, 기본값 변경과, 링크된 SQLite 버전에 네이티브 `DROP COLUMN`이 없는 경우의 순수한 삭제에
대해서는 DBFlux가 `main` 스키마의 단일 테이블에 대해 보수적인 재구축(rebuild)을 사용합니다. 재구축 요청은
해당 열 변경을 삭제와 결합할 수도 있습니다.

재구축은 캐스트, 변환, 백필 없이 유지되는 행을 복사합니다. 검증된 행 식별자와 저장된 값이 그대로 보존되며, 변경된
기본값은 이후 삽입에만 적용됩니다. 따라서 기존 행이 호환되지 않으면 열을 필수로 만드는 작업이
실패할 수 있습니다.

준비는 읽기 전용입니다. 일반 UI와 MCP를 통해 노출되는 미리 보기는 실행 가능한 적용 SQL이 아니라 불변이고 예시를 위한
수명 주기 설명입니다. 드라이버가 private 대체 테이블, 복사와 정확한 비교, 원본 교체, 검증된 명시적 인덱스 복원,
최종 검증을 관리합니다.

각 재구축은 해당 단일 테이블에 대해 원자적입니다. 실패 시 드라이버는 롤백과
연결 설정 복원을 검증합니다. 정리 실패는 계속 표시되며, 불확실한 트랜잭션 상태나 실패한 연결 설정 복원은
재연결까지 해당 연결을 격리합니다. 테이블 간 원자성은 없습니다.

#### 재구축 범위

재구축 경로는 `main` 스키마에서 안전하다고 증명할 수 있는 테이블 형태만 받습니다. 예를 들어 CHECK 제약 조건, 생성된 열(generated columns),
`AUTOINCREMENT`, `STRICT`, `WITHOUT ROWID`, 뷰나 트리거, 표현식 또는
부분 인덱스, 연결된 스키마, 활성 상태의 호출자 소유 트랜잭션은 거부됩니다. 이러한
제한은 재구축에만 적용됩니다: 그 외의 조건을 충족하는 네이티브 순수 삭제는 재구축 문법 밖이라는 이유만으로
거부되지 않습니다.

### 인덱스 작업

**CREATE INDEX**:
- 기간 동안 데이터베이스를 잠급니다(쓰기 차단)
- 동시 옵션 없음 (PostgreSQL과 다름)

**DROP INDEX**:
- 빠름 (메타데이터만 변경)

**REINDEX**:
- 인덱스를 재구축합니다 (데이터베이스 잠금)

### 제약 조건

**제약 조건 추가**:
- SQLite는 `INSERT`/`UPDATE` 시점에 제약 조건을 검증합니다
- 기존 테이블에 제약 조건을 추가할 수 없습니다 (테이블 재생성 필요)

**외래 키**:
- 기본적으로 비활성화됩니다 (`PRAGMA foreign_keys = ON`으로 활성화 필요)
- 기존 테이블에 추가할 수 없습니다 (테이블 재생성 필요)

### 알려진 제한 사항

- 관리형 테이블 변경 플래너는 선택된 타입, nullability, 기본값 변경과 삭제를 수행하며, 기존 테이블에 제약 조건을 추가하지는 않습니다.
- 재구축은 위에서 설명한 검증된 테이블 형태로 의도적으로 제한되어 있습니다.
- 동시 인덱스 생성 없음 (데이터베이스 잠금)
- 동적 타이핑 (열 타입은 참고용일 뿐)

### 모범 사례

1. **수동 DDL에는 트랜잭션을 사용하세요** — 관리형 테이블 변경에는 자동 커밋이 필요합니다.
2. **스키마를 미리 계획하세요** — 나중에 수정하기 어렵습니다.
3. **관리형 ALTER 미리 보기를 검토하세요** — 설명적일 뿐이며, 해당 문을 직접 실행하지 말고 DBFlux를 통해 적용하세요.
4. **지원되지 않는 형태는 별도로 계획하세요** — 재구축 경로는 뷰, 트리거, 기타 검증되지 않은 형태를 거부합니다.
5. **먼저 복사본에서 테스트하세요** — 특히 관리형 재구축 전에 그렇습니다.
6. **외래 키를 활성화하세요** — 스키마를 변경하기 전에 `PRAGMA foreign_keys = ON`을 설정하세요.
7. **VACUUM을 사용하세요** — `DROP TABLE`이나 테이블 재생성 후 디스크 공간을 회수합니다.
