# DBFlux 상표 정책

DBFlux 소스 코드는 `MIT OR Apache-2.0` 라이선스의 자유 소프트웨어입니다. 그러나
**DBFlux**라는 이름, DBFlux 로고, `dbflux.dev` 도메인은 이 허가에 포함되지
않습니다. 이 문서는 별도의 문의 없이 이들을 사용할 수 있는 범위를 설명합니다.
## 빠른 경로

1. 출처를 밝힐 때 이름을 사용할 수 있습니다: "DBFlux 기반", "DBFlux 포크",
   "DBFlux와 호환".
2. **수정하지 않은** 공식 릴리스 아티팩트는 DBFlux라는 이름 그대로 재배포할 수
   있습니다. 예를 들어 Homebrew, AUR, nixpkgs 패키지로 배포하는 경우입니다.
3. **수정한** 빌드를 배포할 때는 다른 이름과 로고를 사용하세요. 프로젝트가
   DBFlux에서 파생되었으며 공식 제품이 아니라고 밝혀야 합니다.

세 가지 경우 어디에도 해당하지 않으면 이 리포지토리에 이슈를 열어 문의하세요.

## 다루는 상표

| 상표 | 의미 |
|------|------|
| DBFlux | 제품 이름. 대소문자 구분 없이, 단독으로 또는 "DBFlux Pro", "DBFlux Nightly" 같은 복합어로 쓰이는 모든 형태. |
| 로고 | `resources/branding/`과 `packaging/icons/` 아래의 모든 파일, 그리고 그 파생물. |
| dbflux.dev | 도메인과 그 아래의 모든 페이지. |

코드 라이선스가 이를 바꾸지 못합니다. Apache 2.0 문서의 6절이 이렇게 규정합니다.
MIT는 상표를 전혀 언급하지 않으므로 Apache 대신 MIT를 선택한다고 해서 Apache가
보류하는 이름에 대한 권리가 생기지는 않습니다.

## 허용되는 사용

| 사용 | 별도 문의 없이 허용 |
|------|---------------------|
| 출처, 호환성, 비교를 설명 ("DBFlux 기반", "DBFlux와 함께 작동") | 예 |
| 포크의 소스 파일, 커밋 기록, 문서에 이름 유지 | 예 |
| DBFlux라는 이름으로 **수정하지 않은** 공식 릴리스를 패키징하거나 미러링 | 예 |
| DBFlux에 관한 기고문, 발표, 튜토리얼 작성. 스크린샷에 로고가 포함되어도 됨 | 예 |
| 공식 릴리스에 없는 패치가 포함된 빌드에 이름과 로고 사용 | 아니요 |
| 다른 리포지토리에서 DBFlux 브랜딩의 릴리스, 설치 관리자, 업데이트 채널 배포 | 아니요 |
| 주요 요소가 "DBFlux"인 도메인, 패키지 이름, 앱 스토어 등록 항목, 계정 등록 | 아니요 |
| 로고 또는 편집한 로고를 파생 제품의 아이콘으로 사용 | 아니요 |

"수정하지 않은"이란 그 아티팩트가 이 리포지토리의 태그에서 공식 릴리스
워크플로로 만들어졌고 체크섬이 릴리스와 함께 게시된 것과 일치함을 뜻합니다.
같은 태그에서 다시 빌드한 결과는 소스 트리가 해당 태그와 바이트 단위로 동일할 때
수정하지 않은 것으로 간주합니다.

## 포크 이름 짓기

파생 제품에는 사용자가 DBFlux와 혼동할 수 없는 이름이 필요합니다. 다음 방식은
가능합니다:

- 출처를 밝히는 짧은 설명이 붙은 별개의 이름: "Fluxbase, a fork of DBFlux".
- 비공식임을 명확히 표시하는 한정어: "DBFlux (community edition, unofficial)"는
  README에서 허용됩니다. 그러나 바이너리, 창 제목, 번들 식별자, 설치 관리자는
  단순히 "DBFlux"로 표시되어서는 안 됩니다.

다음 방식은 불가능합니다:

- 포크에서 "DBFlux vX.Y.Z"라는 이름의 릴리스를 배포하는 것.
- 앱이 여전히 스스로를 DBFlux라고 부르면서 인앱 업데이트 확인을 포크로 향하게
  하는 것.
- DBFlux 아이콘이나 색만 바꾼 아이콘을 앱 아이콘으로 재사용하는 것.

이름 변경이 소스 트리를 건드릴 필요는 없습니다. 표시 이름, 번들 식별자, 아이콘
세트, `repository` 필드, 릴리스 제목만 바꾸면 충분합니다.

## 이 정책이 존재하는 이유

"DBFlux"를 설치한 사용자는 이 프로젝트가 게시한 빌드를 기대합니다: 검토된 변경
사항, 문서화된 데이터 및 개인정보 동작, 플랫폼이 지원하는 경우 서명된
아티팩트가 그 대상입니다. 같은 이름의 수정된 빌드는 이 기대를 깨뜨리며, 그에
대한 버그 리포트가 이곳으로 들어옵니다.
