# AWS Secrets

AWS Secrets Manager and Systems Manager Parameter Store, browsed from one connection.

## At a glance

- **Category** — Secret store
- **Query language** — Secret browser (no query language)
- **URI scheme** — `aws-secrets`

AWS secret-store driver for DBFlux, built on the [`aws-sdk-secretsmanager`](https://crates.io/crates/aws-sdk-secretsmanager) and [`aws-sdk-ssm`](https://crates.io/crates/aws-sdk-ssm) SDKs. Gated behind the `aws_secrets` feature flag.

## Features

- Secret-store driver classified as `DatabaseCategory::SecretStore` with the `SECRET_STORE` capability. One connection exposes two stores through the `SecretStoreSource` seam, in this order: **Secrets Manager** (`secrets-manager`: versions, version labels, rotation, soft delete, writes) and **Parameter Store** (`parameter-store`: versions, hierarchical paths, typed values, writes).
- Connects through an AWS profile/SSO `AuthProfileRef` or static access-key credentials (mutually exclusive: a connection with both a profile and an Access Key ID is rejected on save and on connect), or the default AWS credential chain when neither is set, with an optional endpoint override (for example LocalStack).
- Connecting succeeds when either service answers, so credentials scoped to only Secrets Manager or only Parameter Store still connect.
- The region of a live connection is switched from the Secrets Manager and Parameter Store documents, without editing the profile: the connection is replaced in place, the profile saved on disk keeps the region it was saved with, and the open listings reload in the new region. The offered regions are the ones EC2 `DescribeRegions` reports for the connection's own credentials, so a region the account has not enabled is never offered.
  - The switch needs `ec2:DescribeRegions` on the credentials. Without it (an IAM user lacking the permission, or LocalStack without EC2) the documents quietly show the connection's configured region as a plain label, with no picker, no error toast and a warning in the log for each failed discovery; Refresh asks again, and switching stays available only by reconnecting with the region set in the profile.
- Listing never fetches a value. Secrets Manager lists with `ListSecrets`, including secrets scheduled for deletion. Parameter Store lists with `DescribeParameters` only, never `GetParametersByPath`.
- Server-side pagination on both stores through the services' page tokens, with page sizes clamped to the service limits (100 for Secrets Manager, 50 for Parameter Store).
- Search on the server side: in Secrets Manager a word search over secret names, descriptions and tags (`all` filter: each word of the name, split at `/`, `_`, `-` and similar separators, is matched by prefix, ignoring case, so `b2back` finds `/team/b2back/stage/env`), and a substring match on the full parameter name in Parameter Store (`Name` filter with `Contains`). LocalStack 3 answers the `all` filter as a case-sensitive prefix match on the name instead of a word match, so against LocalStack the search only finds a secret whose name starts with the typed text. The live suite runs against LocalStack, so the word matching itself is not covered there; the fallback below is covered by unit tests. A search that matches nothing is asked once more with the `Name` filter and its pages keep that filter, so an endpoint that does not implement `all` at all still narrows a search the way this store did before the word filter.
- Parameter paths (`/app/prod/db`) are browsed one level at a time: a level returns the parameters directly under the path and the sub-paths below it. A recursive listing returns every parameter under the path. Names without a leading `/` belong to the root.
- Secret details from `DescribeSecret`: name, ARN, description, KMS key (`aws/secretsmanager` when the secret uses the AWS managed key), created, last changed and last accessed dates, rotation state, schedule, window, function, last and next rotation, version count, staging labels, tags, owning service, and deletion date.
- Parameter details from `DescribeParameters` and `ListTagsForResource`: name, ARN, description, type, tier, data type, KMS key, version, last modified date and user, and tags.
- Value retrieval only on an explicit call: `GetSecretValue` (current version, or a version id) and `GetParameter` with decryption (current version, or a version number). `SecretString` and parameter values are returned as text and `SecretBinary` as binary. Values travel as `secrecy` types and are never logged or written into error messages.
- Writing a new version of a value only on an explicit call (`SecretStoreSource::put_value`, under the `WRITE` capability).
  - Secrets Manager uses `PutSecretValue` with the text or binary payload and, for a staged write, the `AWSPENDING` staging label; a `Current` write keeps the service default that moves `AWSCURRENT` to the new version. The write answers with the new version id. `PutSecretValue` re-encrypts with the key the secret already has and takes no key parameter, so a write never changes how the value is encrypted.
  - Parameter Store uses `PutParameter` with `Overwrite`. The driver always sends the parameter's existing type explicitly (`String`, `StringList` or `SecureString`) and its existing data type (for example `text`) instead of omitting them: the SDK's `PutParameter` model makes both optional when updating, and DBFlux does not rely on how the service resolves an omitted one — sending what the parameter already has cannot change it. A parameter whose metadata reports no type or no data type refuses the write rather than letting the service default it. A `SecureString` keeps the KMS key it is already encrypted with; a parameter whose key the service does not report refuses the write instead of re-encrypting under the account default key. Binary values and staged writes have no parameter-store shape and are refused before any call.
  - A secret owned by another service is refused before the write call, naming the owning service and the secret. A secret scheduled for deletion is rejected by the service itself, and the error is surfaced as the driver maps it.
- Rolling back a Secrets Manager secret to an earlier version (`SecretStoreSource::roll_back`, under `WRITE` and `VERSION_LABELS`, classification `Write`). One `UpdateSecretVersionStage` call moves `AWSCURRENT` to the chosen version and away from the version that holds it, and Secrets Manager itself attaches `AWSPREVIOUS` to the version that was current, so both labels move and no value is rewritten or created. The call names the version that holds `AWSCURRENT` when it is made, so a change in between fails at the service instead of moving the wrong label. The driver refuses before the call a roll back to the version that is already current, to a version that holds `AWSPENDING` (it would promote an unfinished rotation), to an unknown version, on a secret with no current version, and on a secret another service owns. The versions come from `ListSecretVersionIds` with deprecated versions included, because `DescribeSecret` leaves out versions with no staging label and a version with no label is a valid target. Parameter Store has no staging labels and refuses it.
- Deleting, under the `DELETE` capability (`SecretStoreSource::delete_secret`), in the two shapes the request type makes explicit.
  - Secrets Manager schedules the deletion with `DeleteSecret` and a recovery window of 7 to 30 days (30 by default; a window outside that range is refused before the call). `ForceDeleteWithoutRecovery` is never sent, so a secret cannot be deleted for good through DBFlux, and an irreversible request is refused even with the name confirmed. The classification is `Destructive`. Scheduling makes the secret unavailable at once, so reads fail until it is restored; the recovery window only bounds how long a restore is possible. The answer carries the date the deletion becomes permanent. A secret another service owns is refused naming the owner, and one whose deletion is already scheduled is refused rather than having its window replaced.
  - `SecretStoreSource::restore_secret` (`RestoreSecret`, under `SOFT_DELETE`, classification `Write`) cancels a scheduled deletion. A secret that is not scheduled for deletion is refused by the driver, because endpoints differ on a restore with nothing to restore.
  - Parameter Store deletes with `DeleteParameter`, which cannot be undone: the parameter and its history are gone. The classification is `AdminDestructive`, and the request carries the name typed back, which must equal the parameter's name exactly (case and whitespace included) or the deletion is refused before any call. It has no recovery window, so a scheduled request is refused.
- Rotation, under the `ROTATION` capability, in two operations (both classification `Write`).
  - `SecretStoreSource::rotate_now` calls `RotateSecret` with `RotateImmediately` and the rotation already configured. `RotateSecret` also switches automatic rotation on, so the driver refuses a secret whose rotation is not enabled or that has no rotation function instead of enabling it as a side effect. The answer names the version the rotation creates; the service runs the function asynchronously, so the value changes when it finishes.
  - `SecretStoreSource::update_rotation` turns rotation on with `RotateSecret` (rules with the schedule expression and the window, the Lambda function, and `RotateImmediately` false, so editing never rotates) or off with `CancelRotateSecret`. `CancelRotateSecret` leaves the `AWSPENDING` label of a rotation in progress where it was, so the answer names the version that still holds it (`SecretRotationChange::unfinished_version`) and the audit event records it: until that version's credentials are checked and the label is moved or removed, a later rotation can be refused. The schedule is validated locally before any call: `rate(N days)`, `rate(N hours)` with N of 4 or more (singular unit for 1), or a six-field `cron(...)`; the window is whole hours from `1h` to `24h` and, on an hourly schedule, no longer than the interval, which is checked against the window the secret already has when the update names none; the function is a Lambda ARN. The schedule a secret reports uses the same singular form, so it can be sent back unchanged. `RotateSecret` replaces the rules, so an update that names no window re-sends the window the secret already has. Enabling needs a function, either in the update or already on the secret; turning off rotation that is already off is refused.
- Editing tags, under the `TAGS` capability (`SecretStoreSource::update_tags`, classification `Write`). Secrets Manager uses `TagResource` (it overwrites a key that exists) and `UntagResource`; Parameter Store uses `AddTagsToResource` and `RemoveTagsFromResource`. Neither touches the value or any version. Keys and values are validated before any call (key 1 to 128 characters, value 0 to 256, letters, digits, separators including Unicode ones and `_ . : / = + - @`, no `aws:` prefix, at most 50 tags set at once, no key set twice or both set and removed), and so is the count the update leaves: an update that would end past 50 tags is refused. The two calls are separate; a secret at the quota cannot take a new key before an old one is gone, so when the update both adds and removes and the additions alone would pass 50, the removal goes first. A call that fails after the other landed says which half landed. A secret another service owns is refused.
- Editing the description, under the `DESCRIPTION` capability (`SecretStoreSource::update_description`, classification `Write`).
  - Secrets Manager uses `UpdateSecret` with the description and nothing else, so no secret value or KMS key is sent and no version is created. Up to 2048 characters; an empty description clears it.
  - Parameter Store can change a description only through `PutParameter` with `Overwrite`, which writes the value and creates a version, so the driver implements it as an explicit value-preserving write rather than refusing: it is the only way the service offers. The details pane reaches it through Edit description. It fails closed on everything it cannot prove it preserves. It reads the parameter's metadata first and re-sends the existing type, data type, tier, KMS key (for a `SecureString`) and allowed pattern explicitly; it refuses a parameter whose type, data type, tier or `SecureString` key is not reported, one that has policies, because a rewrite could not keep them, and an `aws:ec2:image` parameter, because the service validates the image after it answers, so a rewrite could report success while the description stays unchanged. It reads the current value with decryption (a denied `kms:Decrypt` fails the change before anything is written) and refuses when that value's version is not the one the metadata described. Right before the write it reads the parameter's version again and refuses if it moved. `PutParameter` has no compare-and-swap, so the window is narrowed to the time between that second read and the write, not closed: a value written inside it is replaced by the value that was read. After the write the new version must be the very next one, and if it is not, the error says so and points to the history, where the overwritten value stays readable. The change creates a version, the answer names it and the audit event records it. A rewrite creates a version like any write: Parameter Store keeps 100 versions per parameter, and at that limit the write deletes the oldest version that has no label, or fails with `ParameterMaxVersionLimitExceeded` when every version is labeled, so a description edit can cost an old version or be refused. Up to 1024 characters, and a description cannot be cleared: a rewrite with no description is not offered, so the change needs replacement text.
- Creating, under the `CREATE` capability (`SecretStoreSource::create_secret`, classification `Write`). It never overwrites: both services refuse a name that exists (`ResourceExistsException`, `ParameterAlreadyExists`), the error is a constraint violation, and the existing value is untouched. The initial value is text and is scrubbed from any failure that echoes it, like a value put: verbatim, and JSON-escaped at any nesting depth, with short escapes (`\n`), `\uXXXX` escapes or a mix of both; overlapping forms are removed as one region. A tag value or a description a failure echoes is scrubbed the same way by the governed write path.
  - Secrets Manager uses `CreateSecret` with the name (1 to 512 letters, digits and `/ _ + = . @ -`), the string value, an optional description, an optional KMS key (the account's `aws/secretsmanager` key otherwise) and the tags. A type or a tier is refused, because a secret has neither.
  - Parameter Store uses `PutParameter` without `Overwrite` with the name (letters, digits and `_ . - /`, a leading slash when it has levels, at most 15 levels, not starting with `aws` or `ssm`, and short enough that the name and the ARN the service counts with it fit in 1011 characters, which depends on the partition and region), the type (`String` by default, `StringList` or `SecureString`), the tier (`Standard`, `Advanced` or `Intelligent-Tiering`; the service default when none is given), an optional description, a KMS key for a `SecureString` only, and the tags, which `PutParameter` accepts only when it creates.
- Version history only on an explicit call (`SecretStoreSource::list_versions`, under the `VERSIONS` capability), metadata only: a row is the version's selector, labels, creation date and, where the store reports it, who wrote it. A row has no value field, so rendering or logging one cannot leak a value, and each version is read through the value retrieval above.
  - Secrets Manager uses `ListSecretVersionIds` with deprecated versions included, so a version with no staging label is listed. Every page is followed and the rows are ordered newest first by creation date. The selector is the version id and the labels are the staging labels.
  - Parameter Store uses `GetParameterHistory` without decryption and follows every page; rows are ordered newest version first. The selector is the version number, the labels are the parameter labels, and the author is the last modifying user. `GetParameterHistory` returns each version's value to the SDK even with decryption off (plaintext for `String` and `StringList`, ciphertext for `SecureString`). The driver never reads it: each entry is mapped field by field to metadata, so returned rows carry metadata only, and a value is read only through `get_value` with the row's selector.
- Secrets owned by another service report their `OwningService`, so the UI can show them as read only.
- The secret store document reaches every write above from its UI, each through the governed write path (`dbflux_ui_document::secret_store::write`), gated on the store's capabilities and never on its id. The details pane has a bottom bar (Edit value, and Rotate now or Edit description, and Delete), a Roll back button on every earlier version, Edit rotation and Rotate immediately in the Rotation section, Edit in the Details and Tags sections and Restore on a secret scheduled for deletion; the row menu offers Rotate now, Edit tags and Delete; the toolbar has New secret or New parameter. Every write except Restore (which only cancels a scheduled deletion and runs on one click) and the value editor's Save (a button, not a dialog) asks first in a dialog that names what it will do, and nothing is written until it is confirmed: Rotate now says it runs the rotation function and creates a new version that becomes current when the rotation finishes, Secrets Manager's delete asks for a recovery window of 7, 14 or 30 days and never offers deleting without recovery, Parameter Store's delete asks for the exact name typed back, and Edit description on Parameter Store says it writes the value again as a new version.
- Errors are mapped by AWS error code: denied access, including a denied `kms:Decrypt` on a `SecureString` parameter or an encrypted secret (`DecryptionFailure`), is a permission error carrying AWS's message, never an empty value; missing secrets, parameters and parameter versions are not-found errors; throttling is marked retriable. Each error names the store and the secret.
- Client identity: every request carries `dbflux-<version>` as the AWS SDK app name, visible in CloudTrail's `userAgent` field.

## Limitations

- The create dialog renders the value types and tiers the store declares in its descriptor (`SecretStoreDescriptor::create_choices`), never a list of its own. Parameter Store declares the types `String`, `StringList` and `SecureString` (the default, and the only one that takes an encryption key) and the tiers `Standard` (the default), `Advanced` and `Intelligent-Tiering`; Secrets Manager declares none, so its dialog asks for neither a type nor a tier. The store still refuses a name it does not know. Whether a description change rewrites the value is judged from the capabilities (a version history with no staging labels), because the descriptor does not say it.
- Creating a secret needs `secretsmanager:CreateSecret` (and `secretsmanager:TagResource` when it carries tags, plus `kms:GenerateDataKey` and `kms:Decrypt` on a customer-managed key), and creating a parameter needs `ssm:PutParameter` (plus `ssm:AddTagsToResource` when it carries tags, and `kms:Encrypt` and `kms:GenerateDataKey` for a `SecureString`).
- Editing tags needs `secretsmanager:TagResource` and `secretsmanager:UntagResource` (plus `secretsmanager:DescribeSecret`), or `ssm:AddTagsToResource`, `ssm:RemoveTagsFromResource` and `ssm:DescribeParameters`. Editing a secret's description needs `secretsmanager:UpdateSecret` and `secretsmanager:DescribeSecret`. Editing a parameter's description needs `ssm:DescribeParameters`, `ssm:GetParameter` with decryption (`kms:Decrypt` for a `SecureString`) and `ssm:PutParameter` (with `kms:GenerateDataKey` and `kms:Encrypt` for a `SecureString`), because it rewrites the value.
- Rotating needs `secretsmanager:RotateSecret` and `secretsmanager:DescribeSecret`, turning rotation off needs `secretsmanager:CancelRotateSecret`, and enabling it needs `lambda:InvokeFunction` granted to Secrets Manager on the rotation function.
- Deleting needs `secretsmanager:DeleteSecret` and `secretsmanager:DescribeSecret`, restoring needs `secretsmanager:RestoreSecret` and `secretsmanager:DescribeSecret`, and deleting a parameter needs `ssm:DeleteParameter`.
- Rolling back needs `secretsmanager:UpdateSecretVersionStage`, `secretsmanager:DescribeSecret` (it checks who owns the secret) and `secretsmanager:ListSecretVersionIds`.
- Secret writes need `secretsmanager:PutSecretValue` and `secretsmanager:DescribeSecret` (the write checks who owns the secret before the call), and parameter writes need `ssm:PutParameter` plus `ssm:DescribeParameters` (the write reads the parameter's type, data type and KMS key first) and, for a `SecureString`, `kms:GenerateDataKey` and `kms:Encrypt` on the parameter's key — the write generates a new data key and re-encrypts, so `kms:Encrypt` alone is not enough under a customer-managed key. A denied write is a permission error carrying AWS's message.
- A connection reaches one region at a time, so replicated secrets are listed in the region the connection is on, and secrets shared from other accounts are not listed. Offering the other regions needs `ec2:DescribeRegions` on the credentials.
- Switching the region (or a database on per-database drivers) reconnects with the password the profile already resolves from its saved sources: a literal, an environment variable, a dotenv file or the system keyring. A password that comes from an external secret provider or an auth-profile reference cannot be resolved on that path, so the switch fails with an error naming the destination instead of connecting without credentials; the same happens when the keyring read fails. Reconnect the profile by hand to pick up such a password.
- Listing counts and sub-paths cover the pages loaded so far. A Parameter Store level is grouped from the page of parameters below the path, so a page can hold few or no direct entries, and a later page can repeat a sub-path an earlier page returned.
- Secrets Manager reports one deletion timestamp (`DeletedDate`), the date the scheduled deletion takes effect. It does not report when the deletion was requested or the recovery window, so a scheduled deletion shows only the date it takes effect ("Deletes on"): no deletion moment and no window are shown or inferred.
- Parameter Store's parameter details report no creation date, last access date or version count: they come from `DescribeParameters`, which does not carry them, and the history call that does is made only by the version listing. A parameter version has a last-modified date and no separate creation date, so that date is what its history row shows as created. Parameter Store has no staging labels, so `version_labels` stays empty there.
- A version is selected by version id in Secrets Manager and by version number in Parameter Store. Staging labels and parameter labels are not accepted as selectors.
- The LocalStack-backed live integration tests require Docker and run with `cargo test -p dbflux_driver_aws_secrets --test live_integration -- --ignored`. LocalStack ignores `MaxResults` on `DescribeParameters`, so Parameter Store pagination is not covered by them.
- The write to a parameter refuses one that is absent when its metadata is read, but the decision to overwrite is the service's: `PutParameter` has no compare-and-swap, so a parameter deleted between the metadata read and the write call meets the service's own answer (AWS refuses to overwrite a parameter that no longer exists) and the window between the two calls is inherent to the API. A local re-check cannot close that window; it would only add a second one.
- LocalStack, the live suite's endpoint, diverges from AWS on two write behaviors, so those behaviors are only assertable against real AWS and the live tests document the divergence in place: AWS rejects `PutSecretValue` on a secret scheduled for deletion with `InvalidRequestException` and LocalStack accepts the write; and LocalStack mangles a binary value written through `PutSecretValue` — its provider base64-decodes the request blob to raw bytes and its read path base64-decodes the stored value again, silently dropping non-alphabet bytes, so a binary write does not round trip. The driver's own write mapping is correct against AWS and pinned by unit tests; a binary round trip through a write is only provable against AWS.
- LocalStack diverges from AWS on roll back: it deletes a version the moment the version loses its last staging label, while AWS keeps it as a deprecated version with no label until the secret holds more than a hundred. Rolling `AWSCURRENT` back therefore also removes the version that held `AWSPREVIOUS` there, and a version that has been out of the labels for a while is not a target on LocalStack. The live test asserts the labels that matter and tolerates that version being gone; the deprecated-version target is covered by unit tests.
- LocalStack accepts `RestoreSecret` on a secret that is not scheduled for deletion, so the driver refuses that case itself and the behavior is the same on both endpoints. Scheduling and restoring a secret behave as on AWS in the live tests (the date the deletion takes effect is reported and the value is unreadable until the restore), and so does deleting a parameter.
- LocalStack validates that the rotation Lambda function exists when rotation is enabled (`ResourceNotFoundException: Lambda does not exist`), and the live suite starts no Lambda service. Enabling rotation, rotating now and turning rotation off therefore have no live coverage: their planning (schedule, window and function validation, keeping the existing function, refusing a rotation that is off) is unit tested, and the calls themselves are only provable against real AWS. The live suite covers the refusals that happen before any call.
- LocalStack's `DescribeParameters` does not report a parameter's tier, so a Parameter Store description change is refused there (it will not guess the tier of a value it is about to rewrite) and the change can only be proven end to end against real AWS. The live test pins the refusal and that nothing is written; the planning, the version checks and the fake store's behavior are unit tested.
- Creating a Secrets Manager secret with a customer-managed KMS key, and a `SecureString` parameter with a named key, are not exercised by the live suite: LocalStack answers those calls without checking the key, so what is proven there is the call shape, and key permissions are only provable against real AWS.
