About

Why DBFlux exists

Every database client eventually asks you to pick a side. DBFlux takes the third option.

That constraint is enforced in the code, not in a style guide. The interface adapts through capability flags and metadata, so a document store gets a document view and a time-series store gets a range picker without a single branch on a driver name. Adding a database is writing a driver, not patching the app.

The long-term goal is stated plainly on the README: one fully open-source client for every database you work with. Rust and GPUI are how it stays fast enough to be worth switching to.

Built in the open. Dual-licensed MIT or Apache-2.0, at your option.

The third option
Option one

Fast, but one engine

A native client that speaks a single database well, and leaves you with another app for everything else.

Option two

Universal, but slow

A client that speaks all of them and makes you wait on a heavy runtime for every tab you open.

The third option

One core, drivers that plug in

A driver-neutral core, drivers that plug into it, and a UI that never learns the name of any of them.

Principles
01

Keyboard before pointer

If an action exists, it has a binding and a command-palette entry. The mouse is a fallback, and no workflow depends on it.

02

The UI never knows a driver’s name

Category, query language and capability flags decide what renders. A driver that needs new behaviour adds a seam to the core rather than a special case to the interface.

03

Dense over decorative

Cut corners on controls, hard edges on data, one accent colour. Screen space belongs to your data.

04

Nothing runs unrecorded

Queries, hooks, scripts and AI tool calls all write to the same audit log, redacted by default and yours alone. It never leaves the machine.
