Import · SQL script

Import wizard: run a SQL script

Choosing a .sql file in “Choose File…” starts a “Run SQL script” flow in the import wizard, only on SQL connections. Configure shows what the script holds before anything runs; Confirm summarises the script, with a danger block when it has destructive statements; Running shows progress and a way to stop; Done says what happened to the statements that ran. Every refused option or failure says why and what to do.

Note“Choose File…” now also accepts .sql. On a connection whose query language is SQL, choosing one opens the “Run SQL script” flow in this same wizard: the dialog title changes, the rail keeps Pick Source, Configure, Confirm, Run, and the script is read and split at once. The line under “Choose File…” lists every importable kind, so nobody has to guess what the button takes.
NoteOn a connection that is not SQL, the file dialog does not offer .sql at all, so a script cannot be picked by mistake. The refusal in state 14 is only a backstop for a file that gets through anyway, for example by switching the dialog to all files.
NoteA script is read as UTF-8 and split into statements with the same splitter the editor uses, which respects quotes, comments and dollar-quoted bodies. It has no delimiter or encoding options, so Configure carries none.

NoteA run that stops ends on Done instead of closing: it names the statement (number, line and text), shows the database’s own message, says what happened to the earlier statements, and ends with what to do. The wording of the error is the driver’s. Every failure is also reported once as a toast with “View in Audit”.
NoteCancel Run asks the driver to stop the statement in progress. In one transaction the run then rolls back; without one, the statements already run stay. Both outcomes are stated on the Running footer before the user presses it, and again on Done.

The other Pick Source errors

Unreadable file:
Cannot read the file: ~/dumps/shop_restore.sql: Permission denied (os error 13)Check that you can read the file, or choose another one.
Not UTF-8:
Cannot read the script: it is not valid UTF-8 (invalid byte at position 1,204).SQL scripts are read as UTF-8 and have no encoding option. Save the file as UTF-8 in your editor and choose it again.
Too large:
This script is 240 MB, over the 100 MB limit for running a script here.Run it with the database’s own command-line client instead, or split it into smaller files.
Client directive (DELIMITER, or a GO batch separator line):
This script uses the client command DELIMITER (line 12), which only the mysql command-line client understands.Run it with the mysql client, or remove the DELIMITER lines and end each statement with a semicolon.
psql data block or meta-command (COPY … FROM stdin rows ending with \., or a line starting with \ such as \connect or \set):
This script has a COPY … FROM stdin data block (line 48), which only the psql command-line client can load.Run it with psql, or re-create the dump with INSERT statements (pg_dump --inserts).
Empty script:
The script has no statements: the file is empty or holds only comments.Choose a file that has at least one statement.
Unsupported type:
Only .csv, .json, .jsonl, .xml, .xlsx, .xlsm, .xls, .ods and .sql files can be imported.Choose a file with one of those extensions.
NoteEach error keeps the user on Pick Source with both buttons enabled, in the same error block as the other source errors. A connection that is not SQL is refused here, before any statement is read, because a script cannot run there. This is a backstop: the file dialog already hides .sql on those connections. A script over 100 MB, or one that uses a client directive (a MySQL DELIMITER line, a GO batch separator line, a psql COPY … FROM stdin data block or a psql backslash meta-command such as \connect or \set), is refused the same way, before anything runs.
